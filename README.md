# Лабораторная работа №2. Веб-приложение с уязвимостями

### ДИСКЛЕЙМЕР!!!

Это учебный проект для лабораторной работы. Все уязвимости внедрены специально, для демонстрации.
Запускать приложение можно только локально (на `127.0.0.1`) или на
отдельной виртуальной машине без доступа в интернет. Использовать
код или показанные техники против чужих сайтов и систем нельзя —
это только для учёбы и показа того, как работают уязвимости из OWASP Top 10.

## О чём вообще приложение

Я сделала небольшое веб-приложение на Flask под названием «Мои
Заметки» — простой сервис для личных заметок: можно
зарегистрироваться, войти и оставлять текстовые заметки. Все заметки
при этом видны на одной общей странице (в интерфейсе это не
афишируется специально, чтобы было похоже на обычный сайт).

## Часть 1 — приложение (`app.py`)

### Библиотеки

- `Flask` — на нём всё приложение: роуты, запросы, сессии, редиректы
- `sqlite3` — встроенный модуль Python, база хранится в файле `lab.db`
- `html` — тоже встроенный модуль, нужен для экранирования, т.к.
  страницы собираются обычными f-строками, без Jinja2

### Как устроен код

- `page()` — общая обёртка страницы (шапка с меню + вставка тела)
- `get_db()` / `close_db()` — подключение к SQLite через `flask.g`
- `init_db()` — пересоздаёт таблицы `users` и `notes` при каждом
  запуске и кладёт туда тестовых пользователей (`admin`, `alice`, `bob`)
- роуты: `/` — главная, `/login` — вход (тут 1-я уязвимость),
  `/logout`, `/register` — регистрация (сделана нормально, без дыр),
  `/notes` — заметки (тут 2-я уязвимость)

### Уязвимость №1 — SQL-инъекция в `/login` (OWASP A03:2021 Injection)

Суть: пользовательский ввод подставляется прямо в текст SQL-запроса
без обработки, из-за чего пользователь может своим вводом изменить
логику запроса.

В коде это выглядит так:

```python
query = (
    "SELECT id, username, role FROM users "
    f"WHERE username = '{username}' AND password = '{password}'"
)
```

Вариант через `--` (комментарий): логин `admin' --` превращает
запрос в

```sql
SELECT id, username, role FROM users
WHERE username = 'admin' --' AND password = 'что_угодно'
```

всё после `--` SQL считает комментарием, поэтому проверка пароля не
выполняется.

Вариант через `OR`: логин `' OR '1'='1` превращает запрос в

```sql
SELECT id, username, role FROM users
WHERE username = '' OR '1'='1' AND password = '...'
```

условие `'1'='1'` всегда истинно, поэтому `WHERE` выполняется
независимо от реальных данных, и запрос вернёт первую строку из
таблицы `users` — то есть тоже можно войти без знания пароля.

### Уязвимость №2 — хранимый XSS в `/notes` (OWASP A03:2021 Injection)

Суть: пользовательский ввод вставляется в HTML-страницу без
экранирования, из-за чего браузер может принять его не за текст, а
за код (тег/скрипт) и выполнить. Если такой ввод сохраняется в базе
и потом показывается всем — это хранимый (stored) XSS.

В коде: при выводе заметок `author` экранируется, а `text` — нет:

```python
notes_html += f'<div class="c"><b>{html.escape(author)}</b>: {text}</div>\n'
```

Если вставить в заметку `<script>alert('xss')</script>`, этот тег
попадёт в HTML как есть и выполнится в браузере у каждого, кто
откроет `/notes`.

### Бонус — небезопасная настройка cookie (OWASP A05:2021)

```python
app.config["SESSION_COOKIE_HTTPONLY"] = False
```

Из-за этого cookie сессии доступна через `document.cookie` в
JavaScript. Само по себе это не дыра, но вместе с XSS выше становится
опасно — украденный скрипт может прочитать и отправить куда-то
чужую сессию.

### Как запустить

```bash
pip install flask
python app.py
```

Поднимется на `http://127.0.0.1:5000`, база `lab.db` пересоздаётся
при каждом запуске.

## Часть 2 — эксплуатация (`exploit.py`)

Отдельный скрипт, который просто ходит по HTTP к уже запущенному
приложению через библиотеку `requests`, как обычный клиент, без
доступа к коду или базе.

Что он делает:

1. Логинится как `admin`, подставляя в логин `admin' --`, и проверяет
   по ответу, что вход прошёл без знания пароля.
2. Отправляет заметку с `<script>alert(...)</script>` и проверяет,
   что при чтении `/notes` payload вернулся без экранирования.
3. Смотрит заголовок `Set-Cookie` и показывает, что флага `HttpOnly`
   там нет.

Запуск (приложение должно быть уже запущено в другом терминале):

```bash
pip install requests
python exploit.py
```

## Часть 3 — патч (`patch.diff`)

Diff-файл, который чинит все три проблемы разом:

- `/login` — переделан на параметризованный запрос
  (`WHERE username = ? AND password = ?`)
- `/notes` — текст заметки теперь тоже проходит через `html.escape()`
- `SESSION_COOKIE_HTTPONLY = True`

Применить его можно так:

```bash
patch -p1 < patch.diff
# или
git apply patch.diff
```

После патча `exploit.py` уже не сработает — вход требует правильный
пароль, а XSS-нагрузка выводится в экранированном виде.
